# Sample resume for ATS testing

A fictional candidate used to test whether an ATS reads a document correctly.
**Nothing here is a real person.** Every employer, school, metric and project is
invented, so this file can be uploaded anywhere without consequence.

## Files

| File | |
|---|---|
| `Jordan-Sample-Resume.docx` | Upload this one. Generated by the tool's own DOCX writer. |
| `Jordan-Sample-Resume.pdf` | Same content as PDF. Text-based, 1 page, 286 words extractable. |
| `Jordan-Sample-Resume.txt` | Plain-text self-test. Open it and read it top to bottom. |
| `resume.md` | The source. Edit and regenerate. |
| `profile.md` | The fictional source of every claim in it. |

Regenerate after editing `resume.md`:

```sh
cd ~/resume-forge
python3 forge.py lint sample/resume.md                  # must be clean
python3 forge.py pdf  sample/resume.md sample/Jordan-Sample-Resume.pdf --verify
python3 -c "
import pathlib, docx_writer, lint
md = pathlib.Path('sample/resume.md').read_text()
pathlib.Path('sample/Jordan-Sample-Resume.docx').write_bytes(docx_writer.build_docx(md, 'Jordan Sample'))
pathlib.Path('sample/Jordan-Sample-Resume.txt').write_text(lint.plain_text_export(md))"
```

The PDF comes from headless Chrome's print engine — the same path the browser
print dialog uses, with no PDF library and no rasterization. `--verify` extracts
the text and tells you whether the result would parse as a document or as a
blank scan.

## What the generator guarantees

Verified structurally, part by part:

- Valid zip, every part parses as XML
- US Letter, 0.75in margins, single column, 13pt line spacing
- Calibri 10.5pt body, 16pt name, black text only
- No tables, no text boxes, no images, no text in headers or footers
- Standard section headings: Summary, Skills, Experience, Projects, Education
- Real bullet list formatting via `numbering.xml`, not typed dashes
- En dashes in date ranges (`2021 – Present`), right-aligned by tab stop
- No pronouns, no trailing periods on bullets, no vague quantifiers
- Text survives a full round trip out of `word/document.xml`

## Upload both, compare

Upload the `.docx` **and** the `.pdf`. Some portals accept both and some ATS
processes extract them differently, so which one parses cleanly is worth knowing
for the specific system you are targeting rather than assuming.

Both are produced from the same `resume.md`, so any difference between them is a
difference in the exporter, not in the content.

**Then check these five things**, in order of how often they break:

1. **Does the name appear at the top?** If it is missing, something structural
   went wrong — this document puts the name in a normal paragraph, so a parser
   losing it is telling you about the parser, not the file.
2. **Is "Experience" recognized as a section?** Not just as bold text — as a
   section with the jobs under it.
3. **Are the dates attached to the right job?** Meridian Payments `2021 – Present`
   and Brightline Labs `2019 – 2021` must not swap or merge.
4. **Do the bullets come out as bullets?** Nested under the right role, not
   pooled at the end.
5. **Open the `.txt` side by side.** Anything missing or reordered in the
   parser output but present here is a parser loss you cannot fix with wording.

## If it scores badly

Score is a weak signal and the tools disagree with each other. Before changing
the document, change one thing at a time and re-upload. The most common causes,
in order:

- Two-column or table layout
- Contact details in a header or footer
- Body text under 10.5pt
- An unusual font that gets substituted, taking adjacent text with it
- A header the parser expects and does not find

## To test the contrast

Want to confirm the simulator is worth anything? Generate a deliberately hostile
variant — table layout, 8pt text, contact details in a header, pronouns, vague
quantifiers — and upload both. If the hostile one scores the same, the simulator
is measuring almost nothing and its score should not guide your resume.

That variant is not built yet. Ask for it and it is a few minutes of work.
